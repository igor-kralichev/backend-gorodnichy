# Архитектура backend

## Стартовая единица развёртывания

Текущий контейнер `api` — первый сервис платформы: **Entity Schema Service**. Он реализован как отдельное FastAPI-приложение с внутренними слоями:

```text
HTTP API -> application use case -> domain contract -> SQLAlchemy/Redis adapters
```

На первом этапе в одной миграционной цепочке зафиксированы и таблицы следующих контуров. Это позволяет стабилизировать идентификаторы и модель данных до подключения фронтенда. При выделении следующего сервиса его таблицы и миграции переходят к новому владельцу; после этого другие сервисы не записывают в них напрямую.

## Целевые сервисы

```text
Vue SPA
  |
API Gateway / BFF
  |-- Identity Service       пользователи, организации, JWT/OIDC, RBAC
  |-- Entity Schema Service схемы, поля, версии, публикация, OpenAPI-метаданные
  |-- Dictionary Service    справочники и поиск значений
  |-- Registry Service      объекты, валидация, PostGIS, история изменений
  |-- Import Service        пакетный импорт и геокодирование
  |-- File/Report Service   S3/MinIO, фото, документы, PDF/ZIP
  `-- Geo Adapter Service   DaData, Overpass, Nominatim, rate limit и кэш

Transactional outbox -> Redis Streams (локально) -> consumers
```

Identity Service интегрируется с Keycloak как OIDC-провайдером, а не хранит пароли в прикладном сервисе. API Gateway может проверять токен первым, но каждый сервис повторно проверяет подпись JWT и права на конкретную сущность. В локальном контуре Keycloak запускается в Docker, realm roles `Admin` и `User` создаются при импорте realm.

## Владение данными

- Один PostgreSQL-кластер допустим локально и на раннем production-этапе.
- У каждого сервиса должен быть отдельный пользователь БД и своя схема либо отдельная БД.
- Только владелец таблиц выполняет запись. Межсервисные JOIN запрещены в прикладном коде.
- Для чтения чужих данных используются HTTP/gRPC или локальная read model, обновляемая событиями.
- PostGIS-геометрия принадлежит Registry Service.
- Бинарные файлы хранятся в S3/MinIO; PostgreSQL содержит метаданные в `attachments`, `object_key` файла и денормализованный массив `entity_objects.attachment_paths` для быстрой выдачи путей объекта.
- Redis не является источником истины: потеря кэша не должна приводить к потере сущностей или объектов.

Локальный Compose использует постоянные volumes. Пересборка образа или контейнера не пересоздаёт кластер PostgreSQL. Структуру меняет только последовательная миграция Alembic.

## Создание сущности

1. Gateway передаёт команду в Entity Schema Service с JWT Keycloak.
2. Pydantic проверяет контракт, типы полей, ссылки и настройки карты.
3. Application service создаёт в одной транзакции `entity_schemas`, поля, геометрии, стили и версию схемы.
4. В той же транзакции появляется `outbox_events(entity_schema.created.v1)`.
5. После commit схема помещается в Redis. Ошибка Redis не откатывает сохранённую сущность.
6. Outbox publisher отправляет событие в Redis Streams; Registry, Dictionary и Gateway обновляют свои read models/кэши идемпотентно по `event_id`.

Создание, изменение и публикация формируют неизменяемые записи в `entity_schema_versions`. При переходе к отдельному Registry Service объект должен дополнительно хранить номер версии схемы, по которой он прошёл проверку. Это исключит ситуацию, когда изменение конструктора внезапно делает старые записи невалидными без явной миграции.

Публикация сущности с геометрией материализует `entity_layers`. Слой хранит эффективный стиль, прозрачность, возможность выбора и видимость по умолчанию. Изменение схемы синхронизирует слой в той же транзакции, архивирование отключает его, а восстановление оставляет выключенным до новой публикации.

## Runtime API

Автогенерация не должна создавать Python-файлы и таблицы для каждой сущности. Registry Service предоставляет универсальные маршруты:

```text
POST   /api/v1/entities/{entityCode}/objects
GET    /api/v1/entities/{entityCode}/objects
POST   /api/v1/entities/{entityCode}/objects/search
GET    /api/v1/entities/{entityCode}/objects/{objectId}
PATCH  /api/v1/entities/{entityCode}/objects/{objectId}
POST   /api/v1/entities/{entityCode}/objects/{objectId}/archive
POST   /api/v1/entities/{entityCode}/objects/{objectId}/restore
DELETE /api/v1/entities/{entityCode}/objects/{objectId}
```

Маршрут загружает опубликованную версию схемы, валидирует `values` и GeoJSON, строит параметризованный SQL и сохраняет объект вместе с событием истории. OpenAPI строится динамически из опубликованных версий по `/api/v1/openapi.json`, а отдельный Swagger доступен по `/api/v1/generated/docs`; исполняющий код остаётся общим и тестируемым.

Иерархия low-code объектов строится универсально: схема сущности может ссылаться на родительскую схему через `parent_entity_schema_id`, а объект — на родительский объект через `parent_object_id`. Поэтому «школа → корпус → помещение» и любые другие вложенные модели не требуют новых таблиц. Создание объектов всегда принимает массив команд; одиночное создание — это массив из одного элемента, массовая загрузка — тот же контракт с большим количеством элементов.

Файлы объекта обслуживает отдельный контур File/Report Service. На MVP он находится в этом же FastAPI-приложении отдельным модулем `attachments`, но уже работает как будущий сервис: бинарники лежат в MinIO, метаданные и связь с объектом — в PostgreSQL, внешний контракт не раскрывает прямой S3-доступ. Один bucket содержит папки объектов вида `<object_uuid>/<attachment_uuid>`.

HTTP/REST остаётся транспортом команд и запросов. WebSocket или SSE добавляются только для направленных сервером событий: прогресс импорта, готовность отчёта и уведомления об изменениях. Перенос CRUD на WebSocket не ускоряет БД и ухудшает наблюдаемость, идемпотентность и повтор запросов.

Часто используемые динамические поля получают expression indexes, например `(values->>'district')`. Решение об индексе принимается по статистике запросов и хранится как управляемая настройка схемы, а физическое создание выполняется фоновой миграционной задачей.

## История объекта

Один объект не получает отдельную физическую таблицу. Все события хранятся в `object_events`, при большом объёме — с секционированием по дате или `entity_schema_id`:

- `(object_id, revision)` уникален;
- `before_values`, `after_values` дают восстановление состояния;
- `changes` содержит компактный diff для UI;
- `actor_id`, `occurred_at`, `event_type` отвечают на вопросы «кто, когда и что сделал»;
- изменение объекта и запись события выполняются одной транзакцией;
- оптимистическая блокировка сравнивает переданный `revision` с текущим.

## Надёжность межсервисного обмена

- Никаких распределённых транзакций между сервисами.
- Business row и outbox row фиксируются одной транзакцией PostgreSQL.
- Publisher читает outbox через `FOR UPDATE SKIP LOCKED` и публикует сообщение.
- Consumer хранит обработанные `event_id`, поэтому повторная доставка безопасна.
- Длительный импорт реализуется как job, а не как долгий HTTP-запрос.
- Внешние геокодеры защищаются timeout, retry с jitter, circuit breaker, rate limit и Redis-кэшем.
